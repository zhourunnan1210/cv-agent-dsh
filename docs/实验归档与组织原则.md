# 实验归档与组织原则（v1，2026-09-17）

> 定位：**本文件是约定，不是实现**。实验的设计与执行交给 dsh 这个 coding harness agent
> 自己完成——我们只提供①项目背景与上下文、②本归档原则、③必要的授权与门控。
> 因此这里**不定义** `exp_plan / exp_launch / exp_status / exp_collect` 之类的编排工具
> （原设计的四个工具据此**正式撤销**，见勘误 §12.4）。

---

## 1. 为什么是「归档原则」而不是「实验编排服务」

实验层的真实工作形态是：读文献/代码 → 写脚本 → 跑训练 → 看日志 → 改超参 → 记录结论。
这些动作的**执行者**本来就是 coding agent（dsh 的强项：读写文件、跑命令、看后台任务、
委派子代理），把它们封装成固定工具只会把 agent 的自由度锁死在我们预想的流程里。

我们真正需要固定的是**产物与证据的组织方式**——因为它是：
- 后续论文写作与 `EVIDENCE` 溯源的唯一依据；
- 失败实验回流到失败方法库的入口；
- 复现他人（或三个月后的自己）的唯一线索。

所以：**约定归档结构 + 校验产物齐备 = 我们的全部职责。**

## 2. 目录结构（冻结）

```
<project-root>/
└── experiments/
    ├── INDEX.md                    ← 实验总表（id / 一句话 / 状态 / 结论指向）
    ├── _template/                  ← 新建实验时复制这份
    │   ├── README.md
    │   ├── EVIDENCE.md
    │   └── (config/ code/ runs/ 空目录占位)
    └── E001-short-slug/            ← 一个实验 = 一个目录，永不改名
        ├── README.md               ← 假设、变量、成功判据、与哪条 idea/问题对应
        ├── EVIDENCE.md             ← 数字 → 产物文件/命令 的溯源表
        ├── config/                 ← 超参、数据划分、随机种子（进版本控制）
        ├── code/                   ← 只放**入口脚本与改动过的文件**；大依赖走引用
        ├── runs/                   ← 每次运行一个子目录：runs/<YYYYMMDD-HHmm>-<shorthash>/
        │   ├── cmd.txt             ← 完整启动命令（可直接复制重跑）
        │   ├── env.txt             ← 依赖版本 / CUDA / 硬件
        │   ├── stdout.log
        │   ├── metrics.json        ← **机器可读**的最终指标
        │   └── artifacts/          ← checkpoint / 图 / 预测（大文件可外链）
        └── RESULTS.md              ← 结论（含负面结论）、与成功判据的对照、下一步
```

命名规则：

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 实验 ID | `E<三位序号>-<短语义 slug>`，序号**只递增**，不复用 | `E007-freq-branch-ablation` |
| 运行 ID | `<YYYYMMDD-HHmm>-<git 短 hash>` | `20260917-1432-a1b2c3d` |
| 基线与变体 | 变体写在**同一实验**的 `config/` 里，不要另开实验目录 | `config/baseline.yaml` / `config/variant-spectral.yaml` |

## 3. 三条硬规则

### 规则 1：任何数字都要能指回产物

论文/报告里出现的每个数字，必须能在 `EVIDENCE.md` 里找到一行：

```markdown
| 数字 | 含义 | 来源 | 复现命令 |
| --- | --- | --- | --- |
| 93.2 | FF++ c23 帧级 AUC | runs/20260917-1432-a1b2c3d/metrics.json#auc | python code/eval.py --run 20260917-1432-a1b2c3d |
```

- 来源必须到**文件 + 字段**，不接受「我记得跑过」「上次那个日志里」。
- 数字若来自论文引用而非本实验，写 `source: paper:<paper_id>` 并注明页码/表号。

### 规则 2：失败的实验同样归档，并回流失败方法库

- 跑不通 / 指标不升 / 结论为负 → **照常建目录、照常写 RESULTS.md**，不要删。
- 结论为负的实验，须在 `RESULTS.md` 末尾写明是否回流到失败方法库（`failures`）：
  失败模式（`method_invalid` / `data_issue` / `metric_not_improved` / `resource_infeasible` /
  `reproducibility`）、成立条件、以及「什么条件下值得再试」。
- 这条的意义：避免三个月后重跑同一个坑；也是 idea 打分前的复查依据。

### 规则 3：一次运行必须能原地重跑

`runs/<id>/` 里三件套缺一不可：`cmd.txt`（完整命令）、`env.txt`（版本/硬件）、
`config/` 快照（或指向 config 的 hash）。随机种子写进 config，不写在代码里。

## 4. 与状态机 / 门控的衔接

| 时机 | 谁做 | 落点 |
| --- | --- | --- |
| 进入 experiment 阶段 | Orchestrator | 建 `experiments/E<序号>-<slug>/`（复制 `_template/`），README 写清假设与成功判据 |
| 每次运行 | coding agent（dsh 自己） | 写 `runs/<id>/`，**不打断**，失败也留档 |
| 实验收敛 | Orchestrator + 用户门控 | 写 `RESULTS.md` + `EVIDENCE.md`；更新 `INDEX.md`；负结论回流 `failures` |
| 需要 GPU / 计费 API / 破坏性操作 | **主 Agent 先取授权** | 走 §4.6 的 `Authorization`（子代理不能中途发起审批，E15） |

> ⚠️ 关于「让 agent 自己查实验文档」：这是**刻意**的。Orchestrator 只提供项目背景与
> 本原则的路径；具体去读哪个文档、怎么设计实验，由 coding agent 自己决定——
> 我们不用工具把它框死。唯一强制的是**产物齐备性校验**（§5）。

## 5. 校验：`scripts/check-experiment.mjs`

归档原则如果没有校验，就只是愿望。因此提供一个只读校验脚本：

```bash
node scripts/check-experiment.mjs experiments/E001-short-slug      # 单个实验
node scripts/check-experiment.mjs --all                            # 全部实验
```

校验项（缺一即报 FAIL，但不修改任何文件）：

| # | 检查 |
| --- | --- |
| 1 | `README.md` 存在且含 `## 假设` / `## 成功判据` 两节 |
| 2 | 至少一个 `runs/<id>/`，且每个 run 含 `cmd.txt` / `env.txt` / `metrics.json` |
| 3 | `RESULTS.md` 存在；若任一 run 的 metrics 未达成功判据，需显式写 `## 负面结论` 一节 |
| 4 | `EVIDENCE.md` 存在，且**每条数字行都带 `runs/` 路径或 `paper:` 前缀** |
| 5 | `INDEX.md` 里有该实验的一行 |

> 用它的正确时机：实验收敛时跑一次（把 FAIL 项补全），以及 Orchestrator 在
> `cvagent_state_advance` 之前跑一次（把结果写进阶段摘要）。

## 6. 最小上下文包（给 coding agent 的东西）

启动一个实验时，Orchestrator 只需给这几样（其余让它自己查）：

1. 实验 ID 与目录路径；
2. 对应的问题卡 / 方法卡 / 创新卡条目 ID（`P00x` / `M00x` / `I00x`）与一句话说明；
3. 成功判据（要提升哪个指标、在哪个数据集、比谁好）；
4. 已知的失败先例（失败方法库里相关条目，若在阶段 3 已完成复查）；
5. 本文件的路径。

**不要**把论文全文或三库全量塞给它——那是 Reader/Analyst 的活，且违反上下文洁净原则。
