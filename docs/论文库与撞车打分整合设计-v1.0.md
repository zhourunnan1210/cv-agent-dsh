# 论文库结构与撞车 / idea / 打分四层整合设计 v1.0

- 日期：2026-09-17
- 状态：**设计稿，待评审**（不含实现；施工顺序与验收标准见 §9）
- 关联：`CV-Research-Agent_勘误与修订设计-v1.3.md`（本设计修订其 §11 的判据分工与 §5.3 的提取契约）
- 起因：用户的判断——「整个 agent 实际上由论文库整理得好不好决定」；以及「撞车链路 5 段太复杂，
  因为它没有和已有的高度结构化的论文库结合」

---

## 0. 一句话结论

**四个问题（撞车 / idea / 打分 / 论文库）不是四件事，是一件事的四个面。**

论文库的结构决定了"同类"能被表达成什么；撞车、idea 生成、打分都必须读同一套结构。
现状的四个结构性不对齐，是本文档要修的全部内容：

| # | 结构性缺陷 | 后果 |
| --- | --- | --- |
| 1 | 库是**概念中心**（条目→论文有指针，论文→条目没有索引） | "取一篇论文的完整信息"要扫四张表反查，撞车链路只能绕路 |
| 2 | **粒度不对齐**（idea 短、条目长；且 Jaccard 按并集归一化） | 实测：**idea 写得越详细，系统越认为它新颖** |
| 3 | **撞车不可表达**（只能"整体像不像"） | "3 个模块里已有 2 个"这种最常见的撞车形态，系统无法表达 |
| 4 | **相似度越权**（驱动 novelty 分数 + 作为数字锚定裁判） | 实测：同义改写 0.004、同词乱序 1.000 —— 一个无语义的数在当判据 |

## 1. 现状体检（全部数字为 2026-09-17 真实库实测）

### 1.1 三层库的实际状态

| 层 | 表 | 覆盖 | 形态 |
| --- | --- | --- | --- |
| **L1 元数据** | `papers` | **424 篇** | 20 字段：paper_id / title / authors / year / venue / citation_count / doi / arxiv_id / pmid / url / oa_pdf_url / abstract / source_channel / pdf_status / parse_channel / extraction_quality / md_path / pdf_path / created_at / updated_at |
| **L2 提取** | `paper_extractions` | **21 篇** | 十字段：`problem_statement`（一段）/ `method_summary`（一段）/ `innovations`（数组）/ `future_work` / `limitations` / `benchmarks` / `metrics` / `baseline_methods` / `extraction_quality` / `extracted_at` |
| **L3 条目** | `problems` / `methods` / `innovations` / `failures` | **171 条** | 每条 = `entry_id` + `statement`（一句话到一段）+ `source_papers`（数组）+ `ext`（3–5 个**标签**字段） |

L3 四库的 `ext` 字段各不相同：

| 库 | 条数 | ext 字段 | 归属形态 |
| --- | --- | --- | --- |
| problems | 14 | `detection_target` / `modality` / `benchmarks` | **跨论文簇**（P002 有 18 篇来源、P001 有 8 篇） |
| methods | 21 | `paradigm` / `backbone` / `training_strategy` / `generalization_target` / `related_problem_ids` | 一篇一条 |
| innovations | **69** | `innovation_type` / `related_problem_ids` / `related_method_ids` | 一篇一条 |
| failures | 67 | `failure_mode` / `conditions` / `evidence` | 一篇一条 |

**实测关联密度**：21 篇已提取论文各自关联 **6–16 条** L3 条目，合计 **226 次**关联。

**覆盖率断崖**：L2 覆盖 **21 / 424 ≈ 5%**。这个数字就是系统当前的能力上限——L3 的 171 条全部来自这 21 篇。

### 1.2 "同类论文"现在只有一条轴

| 可能的"同类"轴 | 现状 |
| --- | --- |
| 同问题 | ✅ 有——但只有 14 个问题覆盖 21 篇，**粒度粗**（18 篇一锅端） |
| 同方法 / 同范式 | ❌ 无归纳。`methods` 一篇一条，只能按 `paradigm` 标签筛 |
| 同机制 / 同模块 | ⚠️ **数据已存在但未被如此使用**——见 §3.5 |
| 同失败条件 | ❌ 无成组归纳（`failures.conditions` 只是文本） |
| 论文 ↔ 论文相似 | ❌ 完全没有这张图 |

### 1.3 四条链路的现状

| 链路 | 现在怎么做 | 病灶 |
| --- | --- | --- |
| **撞车** | 四库各查一次（FTS5 词项 OR），各取 top-10；证据 = `entry_id` + 库名 + 相似度 + **截断 160 字**的 statement；**不展开论文、不读 L2** | 缺陷 1、3、4 |
| **idea 生成** | N 视角各产 3 条；字段扁平：`statement` / `problem` / `method` / `innovation`（**单个字符串**）/ `baselines`；prompt 与 schema **对长度与实质零要求** | 缺陷 2；结构上与库**不同构**，无从对齐 |
| **打分** | **单个**裁判子代理，**只给逐条判定**（collision / superficial）不给分；分数由 core 算：`novelty = 100 × (1 − 相似度)`；撞车维度"封顶 20" | 缺陷 4（相似度驱动分数）；判据与证据粒度不匹配 |
| **库** | L3 由 Analyst 从 L2 归纳；跨论文合并靠 `cvagent_kb_search` 查重 + 归一化 | 缺陷 1（无论文中心视图） |

### 1.4 关键实测数据（本设计的依据）

**（a）相似度的语义能力**（真实条目 M001，115 字）：

| 情形 | `lexicalSimilarity` |
| --- | --- |
| 同一句话，分句顺序颠倒 | **1.0000** |
| 条目原文被完整包含进 287 字 idea | 0.5945 |
| **同义改写**（意思相同、用词不同） | **0.0039** |
| 完全无关 | 0.0000 |

**（b）长度归一化的病态**（Jaccard 按并集归一化；目标条目原文**一字不差地包含**在 idea 内）：

| idea 长度 | 相似度 | `novelty` | 系统判定 |
| --- | --- | --- | --- |
| 250 字 | 0.4459 | 55 | 判撞车 |
| 383 字 | 0.2960 | 70 | 落边界带 |
| 495 字 | 0.2309 | 77 | 落边界带 |
| **651 字** | **0.1785** | **82** | 落边界带 |
| 904 字 | 0.1349 | 87 | 落边界带 |

> ⚠️ 结论：一旦 idea 按"方法 500–800 字"的粒度撰写（§4.1 商定），
> **即使把已有工作的原文照抄进去，相似度也只有 0.18**——跌破 0.30 的"近似同文"阈值，
> `novelty` 直接给 82 分。**粒度改动会让这个缺陷从偶发变成必然。**

**（c）召回现状**（小库下）：

| 查询 | 命中 | 第 1 名 | 判读 |
| --- | --- | --- | --- |
| 中文方法段（持续学习 / 防遗忘）→ methods | 10/21 | M006（HDP 持续伪造检测框架）✅ | FTS 排序抓得到 |
| 中文问题段（跨域泛化不足）→ problems | 7/14 | P002（跨数据集泛化）✅ | 同上 |
| 英文同义查询 → methods | 6/21 | M018（增量伪造检测）✅ | 靠 statement 里夹带的英文术语 |

但注意：**排序由 FTS5 `rank` 决定，不是相似度**（M006 相似度 0.012 排第 1，M018 相似度 0.105 排第 5）。
`lexicalSimilarity` 在检索里**实际上没起作用**——它只在算 `novelty` 时起作用。
且 top-10 已混入共享高频词的噪声（M013 可解释数据集混进"持续学习"查询）。
**库长大到 150+ 条后，top-10 只覆盖 7%，召回才会真成瓶颈。**

## 2. 总览：目标结构与一套共用原语

```
┌──────────────────────────── 论文库（④ 地基）────────────────────────────┐
│                                                                        │
│  L1 元数据（424 篇）                                                    │
│      │                                                                 │
│  L2 提取（十字段 + ★method_modules）         ← 粒度契约与 idea 同源      │
│      │                                                                 │
│  L3 条目（概念层：problems / methods / innovations / failures）         │
│      │                                                                 │
│  ★L3.5 论文画像 paper_profile（论文中心视图，含反向索引）               │
│  ★L3.6 模块清单 module_inventory（可对齐的机制库）                      │
│                                                                        │
└────────────────────────────────┬───────────────────────────────────────┘
                                 │ 供
     ┌───────────────────────────┼───────────────────────────┐
     ▼                           ▼                           ▼
  ② idea 生成                 ① 撞车链路                   ③ 打分链路
  按模块结构产出         三轴并发 → 证据卡 → 模块级对齐    三专家 × 模块判定
     │                           │                     → 讨论一轮
     └──────────► 同一套检索原语（§8）◄──────────┘     → 确定性聚合
```

**核心设计原则**：四层共用**一套结构**（模块）+ **一套检索原语**（结构/字面/语义三种）。

## 3. 第 ④ 层：论文库的结构

### 3.1 L1 元数据

不变。

### 3.2 L2 提取：粒度契约升级（与 idea 同源）

**变更点**：新增 `method_modules`（方法**组成**），并把各字段的**内容与字数要求**写成契约（原先零要求）。

```ts
/** 方法的一个组成模块（不是"创新点"，是"组成"）。 */
interface MethodModule {
  /** 可命名的模块名，如「频域一致性约束」「稀疏回放缓冲」。 */
  name: string
  /** 一句话：它在整体方法里干什么。 */
  role: string
  /** 60–200 字：输入是什么、做了什么操作、起什么作用。 */
  description: string
  /** 模块类别（用于结构检索）。 */
  kind: 'backbone' | 'module' | 'loss' | 'training_strategy' | 'dataset' | 'protocol' | 'other'
}

interface PaperExtraction {
  paper_id: string
  problem_statement: string        // 150–300 字：现象 + 现有方法为何不够 + 核心挑战
  method_summary: string           // 500–800 字：整体方法叙述
  method_modules: MethodModule[]   // ★ 3–6 个：方法的组成拆解
  innovations: string[]            // 3–6 条，每条 60–120 字，必须能命名到「模块/损失/数据集/协议」
  future_work: string[]            // 0–3 条
  limitations: string[]            // 2–5 条，每条 40–100 字，尽量带数字
  benchmarks: string[]             // 只填数据集/基准名（生成器名不算，见 E32/E33 的教训）
  metrics: string[]
  baseline_methods: string[]
  extraction_quality: 'full_text' | 'abstract_only'
  extracted_at: string
}
```

**`method_modules` 与 `innovations` 的分工**（关键）：

| | 表达什么 | 用途 |
| --- | --- | --- |
| `method_modules` | 方法的**组成**（含标准件，如"用 Xception 主干"） | **撞车的对齐对象**——"你的这个模块，库里有没有人做过" |
| `innovations` | 该论文的**增量**（可命名的机制） | 新颖性判断、idea 生成的素材 |

两者都要，因为撞车问的是"组成里哪些已有"，而新颖性问的是"增量是什么"。

**旧数据迁移**：21 篇已提取论文**不重提取**；初始模块清单从现有 69 条 `innovations` 派生（它们本身就是可命名机制），并把 `method_modules` 标记为"仅新提取论文具备"。

### 3.3 L3 条目：概念层（保持，明确分工）

不变，但明确它是**概念中心**的层：一条 = 一个跨论文的概念 + 来源论文集合。
problems 是簇（粗），methods / innovations / failures 是一篇一条（细）。

### 3.4 ★L3.5 论文画像（paper_profile）

**解决缺陷 1**：让"取一篇论文的完整信息"从"扫四张表"变成一次取用。

**新增反向索引表**（迁移）：

```sql
-- 论文 → 条目（现在只有条目 → 论文，这是结构缺陷的根源）
CREATE TABLE entry_sources (
  paper_id TEXT NOT NULL,
  store    TEXT NOT NULL,     -- problems | methods | innovations | failures
  entry_id TEXT NOT NULL,
  PRIMARY KEY (paper_id, store, entry_id)
);
CREATE INDEX idx_entry_sources_entry ON entry_sources(store, entry_id);
```
维护：`TriLibrary.upsert` 时同步写入（与 `source_papers` 同事务）；首次迁移时从四库的 `source_papers` 全量回填。

**画像结构**（由 `kb.getPaperProfile(paperId)` 组装；**实时组装**，不物化——理由见 §10 开放项 2）：

```ts
interface PaperProfile {
  paper_id: string
  meta: { title: string; year?: number; venue?: string; citation_count?: number; pdf_status: string; md_path?: string }
  extraction?: PaperExtraction        // L2 全文（不截断）
  entries: {                          // L3：按库分组
    problems: EntryRef[]; methods: EntryRef[]; innovations: EntryRef[]; failures: EntryRef[]
  }
  modules: ModuleRef[]                // L3.6：该论文贡献的模块
}
interface EntryRef { entry_id: string; statement: string; ext: Record<string, unknown>; shared_with: number }
```
`shared_with` = 该条目除本论文外的来源论文数——**只靠它就能看出"这张卡是不是这篇独有的"**（P002 的 shared_with = 17）。

### 3.5 ★L3.6 模块清单（module_inventory）

**这是"逐模块撞车"的对齐对象**，也是本设计里最关键的新增层。

**为什么它不是新造的**：`innovations` 已经是 69 条**可命名机制**（≈ 每篇 3.3 条，43–148 字，带类型与关联）。
本层做的是**把它当模块库用**，并补两件事：**(a) 同族归一合并；(b) 从 L2 的 `method_modules` 持续汇入**。

```sql
CREATE TABLE modules (
  module_id   TEXT PRIMARY KEY,      -- MOD001
  name        TEXT NOT NULL,         -- 规范名（归一后）
  statement   TEXT NOT NULL,         -- 一段：这个模块是什么、怎么做
  kinds       TEXT NOT NULL,         -- JSON 数组：module | loss | dataset | protocol ...
  origin_papers      TEXT NOT NULL,  -- JSON 数组：用了它的论文
  origin_innovations TEXT NOT NULL,  -- JSON 数组：它来自哪些 L3 innovations（可追溯）
  ext         TEXT NOT NULL DEFAULT '{}',
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
CREATE VIRTUAL TABLE modules_fts USING fts5(module_id UNINDEXED, name, statement, tokenize='trigram');
```

**归纳规则**（由 Analyst 执行，与 L3 同源的归一化）：
1. 新模块名归一化后与已有模块同名 → 合并（`origin_papers` 并集，statement 取更完整的一条）；
2. 名不同但语义同一 → 由 Analyst 判定合并（用 §8 的语义检索取候选）；
3. 不合并 → 新建。

**规模预估**：21 篇 → 69 条起；若 154 篇全部提取完成，约 **450–600 条模块**。
这个规模**不需要向量索引**（勘误 §9.3 实测：1000 条 × 768 维暴力全扫 1.19ms）。

### 3.6 库的层间接口（契约）

| 接口 | 输入 | 输出 | 谁用 |
| --- | --- | --- | --- |
| `kb.getPaperProfile(paper_id)` | paper_id | `PaperProfile` | 撞车证据卡、写作、人工核对 |
| `kb.listModules(query, filters, limit)` | 查询 + 类别/来源论文过滤 | `ModuleRecord[]`（带分数） | 撞车模块轴 |
| `kb.upsertModule(record)` | 模块记录 | 合并/新建结果 | Analyst |
| `kb.papersUsingModule(module_id)` | module_id | `{ paper_id, entry_id }[]` | 撞车展开 |
| `kb.papersSharingProblem(problem_entry_id)` | 问题条目 | `paper_id[]` | 撞车问题轴 |

## 4. 第 ② 层：idea 提出机制（结构化产出）

**解决缺陷 2 的生成端**：idea 必须与库**同构**，否则无从对齐。

### 4.1 idea 结构（替代现有的扁平结构）

```ts
interface IdeaCandidate {
  idea_id: string
  title: string                      // ★ 一句话标题
  problem: string                    // 150–300 字（对 problems 轴）
  method_overview: string            // 200–400 字：整体思路一段
  method_modules: IdeaModule[]       // ★ 3–6 个（对 methods 轴 + 模块对齐）
  innovations: IdeaInnovation[]      // ★ 3–6 条（对 innovations 轴）
  evaluation: {                      // ★ 结构性给出，而非自由文本
    benchmarks: string[]             // 预期在哪些基准上验证
    metrics: string[]
    protocols: string[]              // in_domain | cross_dataset | cross_manipulation | cross_model
    baselines: string[]              // 预期对比对象
  }
  expected_gain: string              // 预期提升（尽量给可量化表述）
  risks: string[]                    // 2–4 条：这条 idea 最可能怎么失败
  lens?: string                      // 产出它的视角
  generated_by?: string
  authorization?: Authorization
}

interface IdeaModule {
  name: string                       // 与库中模块名可比
  role: string                       // 一句话
  description: string                // 200–400 字：输入/操作/作用（★ 方法部分尽量详细落在这里）
  kind: MethodModule['kind']
  /** 预期优势：这个模块凭什么比现有做法好。 */
  expected_advantage: string
}

interface IdeaInnovation {
  statement: string                  // 60–120 字
  kind: 'new_method' | 'new_framework' | 'new_loss' | 'new_dataset' | 'new_benchmark' | 'new_insight' | 'other'
  related_module?: string            // 对应哪个模块
}
```

### 4.2 共同粒度契约（一处定义，Reader 与 Generator 都引用）

**这是"提取与 idea 同步"的落点**：把 §3.2 与 §4.1 的字数/内容要求写成 core 里的一处常量：

```ts
/** 字段粒度契约：Reader 与 Generator 引用同一份，保证两端比较是对等的。 */
export const GRANULARITY: Record<string, { min: number; max: number; requirement: string }> = {
  problem_statement: { min: 150, max: 300, requirement: '现象 + 现有方法为何不够 + 核心挑战' },
  method_summary:    { min: 500, max: 800, requirement: '整体方法叙述，模块之间的关系' },
  module_description:{ min: 200, max: 400, requirement: '输入是什么 / 做了什么操作 / 起什么作用' },
  innovation:        { min: 60,  max: 120, requirement: '必须能命名到模块 / 损失 / 数据集 / 协议' },
  limitation:        { min: 40,  max: 100, requirement: '尽量带数字与条件' },
}
```
Reader 的 prompt 与 Generator 的 prompt 都从这份常量渲染字数要求——**契约只有一个源**（与「派生与校验逻辑只有一份」同一条纪律）。

### 4.3 生成流程（沿用 N 视角）

```
视角来源：problems 库的 statement（跨论文问题簇）        ← 不变
每个视角：Generator 子代理 → 产出 3 条**模块化** idea
合并去重：按 problem + 模块名集合的归一化键去重          ← 强化（原先只按文本相似）
落盘：idea 存入项目状态（供打分与复查）
```

**新增一步**：生成前把**该视角下的模块清单摘要**（`listModules` 按 problem 关联取 top-N）喂给 Generator，
让它**先知道库里有什么模块**再提 idea——这样产出的 idea 天然是"在已有基础上做增量"，
而不是凭空想象一个库里早就有的东西。**这一步同时降低撞车率与提升 idea 质量。**

## 5. 第 ① 层：撞车链路（三步版）

**替代原 5 段设计**（那段之所以复杂，是因为没利用 §3.5 的结构）。

### 5.1 三步

```
输入：结构化 idea（§4.1）
  │
  ├─ 第 1 步：三轴并发召回（确定性，无 LLM）
  │    问题轴：idea.problem            → problems 条目 → papersSharingProblem() → 论文集合
  │    模块轴：idea.method_modules 逐条 → listModules()        → ModuleRecord + 所属论文   ★核心
  │    做法轴：idea.method_overview    → methods 条目          → 论文集合
  │    并集去重 → 候选论文（默认 12 篇；每轴的排名分别记录，供证据卡排序）
  │
  ├─ 第 2 步：证据卡组装（确定性）
  │    每篇候选论文 → kb.getPaperProfile() → EvidenceCard（L2 全文 **不截断** + L3 条目 + 命中模块）
  │    卡片排序：三轴排名的融合序（不依赖单一口径相似度）
  │
  └─ 第 3 步：模块级对齐（LLM = 三位专家，见 §6）
       idea 的每个模块 → { new | partial | known } + 引用哪条 ModuleRecord/条目 + 理由
       汇总 → CollisionReport
```

### 5.2 数据结构

```ts
interface CollisionReport {
  idea_id: string
  axes: {
    problem_clusters: { problem_entry_id: string; statement: string; papers: string[] }[]
    module_hits: { idea_module: string; module_id?: string; paper_ids: string[]; similarity?: number }[]
    method_candidates: { entry_id: string; paper_id: string; statement: string }[]
  }
  evidence_cards: EvidenceCard[]
  module_alignment: ModuleAlignment[]
  verdict: 'all_new' | 'partially_known' | 'substantially_known'
  computed_at: string
}

interface ModuleAlignment {
  idea_module: string
  status: 'new' | 'partial' | 'known'
  matched: { module_id?: string; entry_id?: string; paper_id?: string; excerpt: string; similarity?: number }[]
  rationale: string
}

interface EvidenceCard {
  paper_id: string
  meta: { title: string; year?: number; venue?: string }
  extraction?: {                       // L2 全文，**不截断**
    problem_statement: string
    method_summary: string
    method_modules: MethodModule[]
    innovations: string[]
    limitations: string[]
  }
  entries: { store: string; entry_id: string; statement: string; ext: Record<string, unknown>; shared_with: number }[]
  failure_hits: { entry_id: string; statement: string; conditions: string }[]
  axis_ranks: { problem?: number; module?: number; method?: number }
}
```

### 5.3 撞车分级（替代"相似度超阈值"）

| 级别 | 判据 | 系统行为 |
| --- | --- | --- |
| `all_new` | 全部模块判 `new` | 正常进入打分 |
| `partially_known` | 有模块 `partial`/`known`，但仍有 `new` 模块 | **进入打分，且在报告里点名"哪几个模块是已有的"**——这是最常见的形态 |
| `substantially_known` | **全部**模块 `known`，且问题轴也命中同一簇 | 报告标红，建议改设计；**不自动否决**（由用户/后续打分决定） |

**关键变化**：撞车不再是一个"分数够不够高"的是非题，而是**一份模块级的对齐清单**——
"你的 M1 库里没有、M2 与论文 X 的『频域一致性约束』高度重合、M3 是论文 Y 的模块换个场景"。

### 5.4 相似度在这一层的**唯一**职责

- 用于**模块轴召回排序**（在 450–600 条模块里找候选），**块级**语义相似度；
- 用于证据卡里展示"两边对应片段"（**只展示片段，不给裁判看数字**——见 §1.4 的教训）；
- **不参与任何分数计算**（用户 2026-09-17 裁定：相似度退出打分、退出裁判上下文）。

## 6. 第 ③ 层：打分链路（三专家 + 模块级判定 + 一轮讨论）

### 6.1 三位专家（分工互补，非同质评委）

| 专家 | 关注 | 判断依据 |
| --- | --- | --- |
| `method` 方法/架构专家 | 方法设计是否真新：模块、机制、损失与库中已有做法的实质差异 | 模块轴对齐结果 + `modules.statement` |
| `evaluation` 实验/评测专家 | 评测协议是否已被覆盖：基准、指标、跨域设置库里有没有现成的 | benchmarks / protocols / 各论文的实验设定 |
| `domain` 领域/问题专家 | 问题是否已被解决：同一问题簇内是否已有工作在同类条件下成立 | 问题轴簇 + 失败库的 `conditions` |

三者互不可见对方的材料（独立委派、独立上下文），与 §11.8 约束 4「生成者 ≠ 裁判」一致。

### 6.2 判断单元是**模块**，不是整段

每位专家输出：

```ts
interface ExpertVerdict {
  expert: 'method' | 'evaluation' | 'domain'
  module_verdicts: {
    idea_module: string
    status: 'new' | 'partial' | 'known'
    evidence_refs: string[]        // 引用哪些 module_id / entry_id / paper_id
    reason: string                 // 理由（这是 LLM 的核心产出）
  }[]
  /** 四维分：由**模块判定**推导，不是拍脑袋给总分。 */
  dimension_scores: ScoringDimensions
  rationale: string
}
```

**四维分如何从模块判定来**（每位专家各自推导，规则写在 prompt 里使其可比）：

| 维度 | 推导依据 |
| --- | --- |
| `novelty_problem` | 问题轴：该问题在库中是否已被明确解决（簇内是否有工作在同一条件下成立） |
| `novelty_method` | 模块轴：idea 的模块里 `new` 的比例，以及 `partial` 模块的差异是否实质 |
| `novelty_combo` | 组合：这些模块的**组合方式**是否在库中出现过（单模块都有、但组合没见过 → 组合仍新） |
| `feasibility` | 评测/资源：基准可得性、算力、数据、协议复杂度 |

### 6.3 一轮讨论（用户 2026-09-17 裁定）

**触发条件**（任一满足）：
- 任一维度三专家 max−min > **15 分**；
- 同一模块出现不同 `status` 判定（如 A 说 `known`、B 说 `new`）。

**讨论怎么组织**（只跑一轮，成本可控）：

```
1. 汇总分歧清单：{ 模块/维度, 三方各自的判定与理由 }
2. 分别发回三位专家（**互见理由**，这是与首轮的关键区别），要求：
   - 对每个分歧点给出"维持/修正"及其理由
   - 修正后的 module_verdicts 与 dimension_scores
3. 第二轮结果即最终输入 → 进入聚合
```

**报告里保留两轮全部原始分与理由**（可审计：能看出谁改了、为什么改）。

### 6.4 确定性聚合（分数可复算）

| 规则 | 内容 |
| --- | --- |
| 维度分 | 三位专家（或讨论轮后）该维度的**中位数**（不用均值——抗离群） |
| 总分 | `sum(维度 × pack 权重)`，权重复算用 `weights_snapshot` |
| 档位 | 按 pack 的 `suggestion_bands`（proceed ≥75 / revise 50–74 / abandon ≤49） |
| 风险级 | 按 `retrieval_mode` 取阈值（保留现有 `classifyRisk`） |
| 分歧标记 | `disagreement: 'none' \| 'resolved_by_discussion' \| 'high'`；`high` = 讨论后仍分歧 > 15 或模块判定仍冲突 → **建议人工复核，不自动降级** |

### 6.5 一致性校验（**替代**"撞车维度封顶 20"）

原规则"撞车则封顶 20 分"是**系统改写专家判断**。改为**校验并如实记录**：

| 冲突类型 | 校验规则 | 报告字段 |
| --- | --- | --- |
| 判定与分数矛盾 | 某专家判某模块 `known`，却在对应维度给高分（> 40） | `consistency.module_score_conflicts[]`（点名专家/模块/维度） |
| 复算不符 | `sum(维度 × 权重) ≠ total` | `consistency.report_consistent = false` |
| 证据缺失 | 给了分但 `evidence_refs` 为空 | `consistency.unsupported_scores[]` |

**分数保持专家所给，不被篡改**；报告如实暴露矛盾。

### 6.6 报告结构（增量修改）

在现有 `ScoringReport` 上增加/替换：

```ts
interface ScoringReport {
  idea_id: string
  pack: { pack_id: string; version: string; frozen: boolean; frozen_by: string | null }
  experts: ExpertVerdict[]                 // ★ 三份原始（首轮）
  discussion?: {                           // ★ 讨论轮（触发时才有）
    round: 1
    disagreements: { target: string; positions: { expert: string; status?: string; score?: number; reason: string }[] }[]
    revised: ExpertVerdict[]
  }
  final_dimensions: ScoringDimensions      // 中位数聚合
  weights_snapshot: ScoringDimensions
  total: number
  band: 'proceed' | 'revise' | 'abandon'
  risk_level: 'low' | 'medium' | 'high'
  module_alignment: ModuleAlignment[]      // ★ 与撞车报告同源
  collision_verdict: CollisionReport['verdict']
  consistency: { module_score_conflicts: string[]; unsupported_scores: string[]; recomputed_total: number; report_consistent: boolean }
  disagreement: 'none' | 'resolved_by_discussion' | 'high'
  retrieval_mode: 'vector' | 'keyword_only'
  computed_at: string
}
```

## 8. 检索原语（统一，四层共用）

| 原语 | 机制 | 擅长的 | 短板 |
| --- | --- | --- | --- |
| **P1 结构检索** | 按 `store` + `ext` 字段 + `related_*_ids` + `entry_sources` 精确查 | 零误召、可解释 | 只能查已标注的维度 |
| **P2 字面检索** | FTS5 词项 OR（现有 `compileFtsQuery`）+ LIKE 回退 | 用词相同时精确 | 换词/换语言即失效（实测同义改写 0.0039） |
| **P3 语义检索** | 本地 embedding **块级**余弦 | 同义、改写、中英混排 | 需模型；需块级切分。**2026-09-18 实测否决**，见 §9.3——本层实际未启用 |

**组合规则（按轴）**：

| 轴 | 主 | 辅 | 说明 |
| --- | --- | --- | --- |
| 问题轴 | P1（`related_problem_ids`）+ P2 | ~~P3~~ | 问题簇是显式结构，优先结构检索 |
| **模块轴** | **P2（FTS5 + LIKE 回退）** | P1（`kind`/`innovation_type` 过滤） | 原计划主用 P3；实测 P3 在真实库上**分不开**且排序不如 P2，改为 P2 主、保留 `Ranker` 端口待换模型 |
| 做法轴 | P2 | P1（`paradigm`） | 方法叙述较长，字面 + 结构字段 |
| 失败轴 | P1（`failure_mode`）+ P2 | ~~P3~~ | 失败条件含数字与设定，字面仍有效 |

**embedding 的定位（修正前一版设计）**：它不是"链路里的一个通道"，而是**P3 的实现**，
原本主要服务**模块轴**——在几百条模块里找对应模块。**这一层实测没通过**（§9.3）：
本地模型把同域短句都压到 0.3–0.5 一带，正例与负例分布重叠，既定不出阈值，排序也不如字面。
当前实现保留为**默认关闭的接入点**（`embeddingEnabled: false`），
换模型（非对称检索模型 / cross-encoder 重排）时可从这里接。

1. **先删掉残留的 `.tmp`**：中断的下载会留下 `onnx/model_quantized.onnx.tmp`，缓存层按最终文件名查找，`.tmp` 等于没有。

### 9.3 4b 的实测结论：**不启用**（用户 2026-09-18 裁定：否决的就不走了）

这一节原本写的是"校准 → 改 pack → 翻 `retrieval_mode`"。**量完之后两条都不成立**，
所以按实测重写。校准脚本：`node scripts/calibrate-vector-thresholds.mjs`（只读库，可复现）。

先说一处**我原来写错的事实**：向量口径不是"不存在"，core 里早就内置了
（`score.ts:152` 向量边界带 `[0.7, 0.9)`；`score.ts:320` 向量 near-dup = pack 的
`high_risk_similarity: 0.85`）。问题是这两个数是**照余弦尺度估的**，没有实测记录。

**标注怎么来的**（不靠人工标）：两条条目**共享至少一篇论文** → 正例；**无共同论文** → 负例。
这是库自身的结构给出的客观标注。它的局限见下。

**实测一：两类分布重叠，没有可用阈值**

| 库位 | 正例 p50 / p95 / max | 负例 p50 / p95 / max | 最佳阈值 J |
| --- | --- | --- | --- |
| problems（14 条，45/46 对） | 0.454 / 0.637 / 0.666 | 0.455 / 0.651 / **0.696** | 0.072 |
| modules（69 条，82/2264 对） | 0.398 / 0.641 / 0.713 | 0.342 / 0.502 / **0.732** | 0.259 |

两处都是**负例最大值高于正例最大值**——不存在同时拿到高召回与低误报的阈值。
现有向量口径在这批数据上的实际行为：边界带 `[0.7, 0.9)` 只覆盖 **1.2%** 的正例，
near-dup `0.85` 的负例触发率 **0.00%**。也就是说，**翻成 `vector` 会让边界带与近似同文
检测双双变成死代码**——不是"更严格"，是"不工作"。

**实测二：语义排序在这个库上不如字面排序**（这才是 4b 真正改的东西）

留一法，用每条条目自己的 statement 作查询，看 top-1/top-5 里有多少条共享论文：

| modules（69 条） | precision@1 | recall@5 |
| --- | --- | --- |
| 语义（余弦） | 24.6% | 40.6% |
| 字面（trigram） | **30.4%** | **63.8%** |

problems（14 条）：语义 50.0% vs 字面 64.3%（n 太小，差 2 条查询，无统计意义）。
methods（21 条）：21 条里没有任何两条共享论文 → 正例为 0，该库位上这个标注无信息。

**这个 A/B 的偏向必须说清**：同一篇论文里的模块常常**名字相近但机制不同**
（实测最高分那对就是 `Token-shuffling branch (S-Branch)` vs `Token-mixing branch (M-Branch)`，
0.713——同一篇论文的两个不同分支）。"共享论文"这个代理标注**天然偏向字面排序**，
而 §6.2 真正要抓的是"**名字不同、机制相同**"，这个标注看不见。
所以这张表能证明的只有一件事：**没有证据支持语义排序更好**。

**因此的处置**（用户 2026-09-18 裁定：**否决的就不走了**）：

1. **不启用语义排序**。`embeddingEnabled` 默认 `false`，`rank_mode` 如实报 `lexical`。
2. **`retrieval_mode` 不翻**，仍是 `keyword_only`。理由不是保守，是实测：向量阈值不工作。
3. **pack 不改、不重新冻结**。没有要写进去的数。
4. 保留 `Ranker` 端口与 `embedding.ts`：它们是这次测量得以进行的前提。
   **这条路不再投入**——下面是"若将来要重开需要什么"，不是待办清单。

**若将来要重开，缺的是一件东西**：一批**人工标注**的"名字不同但机制相同"配对。
有了它才能回答 §6.2 那个真问题，也才能定出向量模式的阈值（若届时分得开）。
在此之前，候选改进方向按代价排序：

- 换 **非对称检索模型**（e5 / bge 系列，带 `query:` / `passage:` 前缀）——当前这个
  `paraphrase-*` 是**对称释义**模型，把同域短句都压到 0.3–0.5 一带，细粒度区分能力弱；
- 嵌入**更长的文本单元**（整段 method + limitations，而不是 20 字的模块名）；
- 用 **cross-encoder 重排**替代双塔阈值——判定"是不是同一件事"本来就是重排任务，
  双塔只适合召回。

另外**未验证的一点**：本次用 q8 量化（112.8MB）。fp32（448.5MB）是否分得更开没有量过，
不能断言量化是主因，也不能断言不是。
